# Технические решения

Игра — ответвление московской «Отделы против дракона» (https://github.com/KonturProject/sales-vs-dragon). Механика, код опроса, админка, анимации простоя и оптимизация под слабые ноутбуки перенесены без изменений; ниже — что нового здесь и почему. Подробную историю решений по общей части см. в `docs/tech.md` московского репозитория.

## Чем отличается от московской версии

| | Москва | Ульяновск |
|---|---|---|
| Группы | СР1, СР2, СР3, СР5, СР6, СР9 | ВШ1, ВШ4, ВШ5, ВШ6, ВШ9, ВШ10 |
| Герои | 6 нарисованных маскотов + Круэлла, зашиты в код | **30 персонажей на выбор**, выбор делается в админке и применяется на экранах без деплоя |
| Фон | пещера (сгенерированная картинка) | каньон на закате из CC0-пакета ansimuz «Gothicvania Rocky Pass» |
| Бэкенд | свой Apps Script + таблица Москвы | отдельный Apps Script «Победи дракона backend» + таблица **«победи дракона»** |
| Репозиторий / ссылка | `sales-vs-dragon` | `sales-vs-dragon-ulyanovsk` (независимая копия: правки в одном репозитории в другой переносятся вручную) |

Дракон, гора золота, HUD, звук, баннер победы, рейтинг, анимации (падение, сон, рычание) — те же.

## Герои: слоты и персонажи

Раньше `HeroSlug` = конкретный персонаж. Теперь это **место на сцене**: `slot_1…slot_6` (отделы слева направо, порядок = `HERO.SLOTS` = порядок `labels` в `ropMapping.json`) и `lead`. По слоту идут события `MONEY_IN`, рейтинг, `IdleMood`, команды админки, бэкенд. Внешность слота — отдельный выбор (`systems/RosterConfig.ts`):

1. Админка → вкладка «Герои» → `setRoster` (`pin`, `roster: {slot_1: 'viking', …}`; ключи — только известные слоты, значения — `[a-z0-9_]{2,32}`; меняются только присланные слоты).
2. Бэкенд хранит JSON в Script Properties (`ROSTER`), **не в таблице**, и отдаёт его в публичном GET (`roster`; `null`, пока ничего не выбрано).
3. `DataPollingService.applyRoster` → `RosterConfig.applySelection` (проверяет id по `characters.json`, мусор игнорирует, сохраняет в `localStorage`) → если слоты изменились, событие `ROSTER_CHANGED`.
4. `PenScene.onRosterChanged` → `loadCharacters` (грузит только недостающие текстуры) → `HeroSprite.setCharacter` (ждёт, пока закончится удар; спящего будит; персонаж «выскакивает» с облачком) / `LeadSprite.setCharacter`; `Leaderboard.refreshColors` подкрашивает строки рейтинга.
5. Выбор кэшируется в `localStorage`, чтобы после перезагрузки экран сразу показывал нужных героев, не дожидаясь ответа бэкенда; значения по умолчанию — `config/heroRoster.json`.

В памяти всегда только 7 персонажей (на сцене) × (стойка + 3 кадра удара) — число доступных персонажей на нагрузку не влияет.

## Персонажи: из 3D в 2D-кадры

Искали открытые (CC0) 2D-наборы анимированных героев не в пиксель-арте; подходящего набора на 30 единообразных персонажей нет (Kenney Toon Characters — 6 статичных поз, остальное либо пиксели, либо CC-BY-SA). Поэтому взят **Quaternius «Ultimate Animated Character Pack»** (CC0, 50+ низкополигональных мультяшных моделей с готовой анимацией: Idle, Punch, Walk…). Модели не хранятся в репозитории; `tools/render-characters/` — помощник (three.js в браузере): для каждого из 30 героев рисует **стойку** (Idle, t=0.3 с) и **три кадра удара** (клип Punch, t=0.18 / 0.30 / 0.42 с) сбоку в три четверти (модель повёрнута на −35°, смотрит вправо), фон прозрачный, 1024×1024.

Особенности моделей, которые пришлось обойти: FBX-материалы приходят полностью прозрачными (`opacity = 0`), цвета записаны линейными, а загружаются как sRGB (`convertLinearToSRGB`), а «кожа» у всех чёрная (замысел автора) — перекрашена в телесные тона, кроме задуманных цветов (гоблин, зомби).

`tools/build-characters.py` превращает рендеры в игровые текстуры: обрезка по рамке, **центрирование по ногам** (нижние строки фигуры), пол — нижний край, **один масштаб на все кадры героя** (стойка = `TARGET_H` = 430 px, в игре ×0.5 → ~215 px на экране), LANCZOS по премультиплицированному альфа-каналу (без тёмных ореолов). Кадр удара ширше стойки (рука вперёд) — холст симметричен относительно ног, поэтому «передний край» оружия = половина ширины текстуры, а подмена кадра не сдвигает героя. Результат — `public/assets/sprites/chars/<id>.png`, `<id>_hit1..3.png` и `config/characters.json`.

Удар теперь покадровый: первый кадр — на старте рывка, средний — в середине, последний (рука вытянута) — на прибытии, когда происходит контакт. Бесконечной анимации стойки нет специально — иначе слабые ноутбуки не уходили бы в экономный режим кадров.

## Фон

`tools/build-scene.py` собирает `bg_scene.jpg` (1280×720) из трёх слоёв пакета (небо, дальние горы, каменная арка; ×3 без сглаживания) и **сгенерированного песчаного пола** в палитре пакета с кристаллами/травой по краям. Пол начинается с y≈438: герои стоят на y 508/578, подножие горы золота — y 530 (см. `HERO.SLOTS`, `DRAGON.MOUNT_*`). Если меняете фон — сохраните эту геометрию или поправьте константы.

## Бэкенд

Тот же `Code.gs` + три отличия: (1) таблицу создаёт сам скрипт — `setupSpreadsheet()` один раз из редактора, id хранится в Script Properties (`SPREADSHEET_ID`), в коде его нет; (2) действие `setRoster` и поле `roster` в GET; (3) допустимые цели команды `fall` — `slot_1…slot_6`. Остальное (PIN хешем + блокировка после 5 ошибок, `addSale` пишет только Date/Amount/ROP в первую свободную строку, команды анимаций в Script Properties, `requestId`-дедупликация) — как в Москве. Подробности API — `apps-script/README.md`.

## Что не проверено вживую / открыто

- Реальные ноутбуки филиала: нагрузка с новыми текстурами (≈40 КБ на кадр, 28 в памяти) не измерялась; при высокой — `?scale=1`, `?fps=20`, см. CLAUDE.md.
- Все 30 персонажей смотрелись на контактных листах, но не каждый по очереди на сцене; «Сакура» (Kimono_Female) названа условно.
- Стойка у всех «тянется» одинаково — индивидуальных поз победы/горя нет.
