# Технические решения

Игра — ответвление московской «Отделы против дракона» (https://github.com/KonturProject/sales-vs-dragon). Механика, код опроса, админка, анимации простоя и оптимизация под слабые ноутбуки перенесены без изменений; ниже — что нового здесь и почему. Подробную историю решений по общей части см. в `docs/tech.md` московского репозитория.

## Чем отличается от московской версии

| | Москва | Ульяновск |
|---|---|---|
| Группы | СР1, СР2, СР3, СР5, СР6, СР9 | ВШ1, ВШ4, ВШ5, ВШ6, ВШ9, ВШ10; у каждой на сцене табличка «ВШ1 • Фамилия И.» с РГ (меняется в админке) |
| Оплаты | вручную через админку | вручную **или импортом выгрузки** «Детальные данные по оплаченным счетам» (.xlsx); при нескольких группах в одном опросе герои бьют по очереди |
| Герои | 6 нарисованных маскотов + Круэлла, зашиты в код | **30 героев на выбор** (7 серьёзных 2D-персонажей AutoSprite + перекраски), выбор делается в админке и применяется на экранах без деплоя |
| Фон | пещера (сгенерированная картинка) | мрачный каньон из CC0-пакета ansimuz «Gothicvania Rocky Pass», затемнённый и охлаждённый, со свечением от золота |
| Бэкенд | свой Apps Script + таблица Москвы | отдельный Apps Script «Победи дракона backend» + таблица **«победи дракона»** |
| Репозиторий / ссылка | `sales-vs-dragon` | `sales-vs-dragon-ulyanovsk` (независимая копия: правки в одном репозитории в другой переносятся вручную) |

Дракон, гора золота, HUD, звук, баннер победы, рейтинг, анимации (падение, сон, рычание) — те же.

## Герои: слоты и персонажи

Раньше `HeroSlug` = конкретный персонаж. Теперь это **место на сцене**: `slot_1…slot_6` (отделы слева направо, порядок = `HERO.SLOTS` = порядок `labels` в `ropMapping.json`) и `lead`. По слоту идут события `MONEY_IN`, рейтинг, `IdleMood`, команды админки, бэкенд. Внешность слота — отдельный выбор (`systems/RosterConfig.ts`):

1. Админка → вкладка «Герои» → `setRoster` (`pin`, `roster: {slot_1: 'viking', …}`; ключи — только известные слоты, значения — `[a-z0-9_]{2,32}`; меняются только присланные слоты).
2. Бэкенд хранит JSON в Script Properties (`ROSTER`), **не в таблице**, и отдаёт его в публичном GET (`roster`; `null`, пока ничего не выбрано).
3. `DataPollingService.applyRoster` → `RosterConfig.applySelection` (проверяет id по `characters.json`, мусор игнорирует, сохраняет в `localStorage`) → если слоты изменились, событие `ROSTER_CHANGED`.
4. `PenScene.onRosterChanged` → `loadCharacters` (грузит только недостающие текстуры) → `HeroSprite.setCharacter` (ждёт, пока закончится удар; спящего будит; персонаж «выскакивает» с облачком) / `LeadSprite.setCharacter`; `Leaderboard.refreshColors` подкрашивает строки рейтинга.
5. Выбор кэшируется в `localStorage`, чтобы после перезагрузки экран сразу показывал нужных героев, не дожидаясь ответа бэкенда; значения по умолчанию — `config/heroRoster.json`.

В памяти всегда только 7 героев (на сцене) × (стойка + 5 кадров удара) — число доступных персонажей на нагрузку не влияет.

## Герои: серьёзные 2D-персонажи, CC0

Историю поиска см. ниже («Что пробовали»). Взяты бесплатные спрайты **AutoSprite** (https://www.autosprite.io/free-sprite-sheets, **CC0**): детальный «нарисованный» пиксель-арт, реалистичные пропорции, не чиби, смотрят вправо — по духу близки к московским героям. В библиотеке 13 персонажей, годятся семь (боком, с бегом): Knight, Hooded Blade, Twin-Dagger Rogue, Arcane Mage, Forest Druid, Alchemist, Ninja. Witch — мультяшная чиби, Goblin — монстр, Paladin/Wanderer/Dancer — «позовые» листы анфас, Red Dragon — дракон: не взяты.

**30 героев = 7 оригиналов + перекраски** (`tools/characters.src.json`): сдвиг оттенка всего цветного, нейтральные (контуры, металл) остаются; у героев с открытой кожей включена `protect_skin`. Перекраски читаются как разные персонажи (стальной/лесной/ночной/золотой рыцарь и т. д.), но это те же силуэты — настоящих 30 разных серьёзных 2D-героев в открытом доступе найти не удалось.

**Удар.** Настоящая анимация удара есть только у Hooded Blade (32 кадра: замах, взмах, горизонтальный выпад) — берутся кадры 2, 9, 14, 15, 16. У остальных удар — это **цикл бега** (4 кадра по кругу) и кадр, где оружие/рука дальше всего выдвинуты вперёд (`forward_reach`: насколько фигура вытянута вправо от своего центра масс). `HeroSprite.playHit` показывает кадры по порядку во время рывка (прогресс твина → индекс кадра), а последний — в момент контакта. Бесконечной анимации стойки нет специально (экономный режим кадров на слабых ноутбуках): в стойке — один кадр.

**Подготовка кадров** (`tools/build-characters.py`): вырезка из атласа (`*.json`), обрезка по рамке, центр — середина рамки стойки, пол — её нижний край, один масштаб на все кадры героя (стойка = `TARGET_H` = 290 px, рисуются с `HERO.TEXTURE_SCALE` = 0.75 → ~215 px на экране), LANCZOS по премультиплицированному альфа-каналу (без тёмных ореолов). Кадр выпада шире стойки — холст симметричен относительно центра, поэтому «передний край» оружия = половина ширины текстуры, а подмена кадра не сдвигает героя. Результат ≈16 МБ на 30 героев; в памяти дисплея только те, кто на сцене (7 × 6 кадров).

**Живая стойка.** Из циклов стойки (`*-idle`, 25–32 кадра) берутся 12 равноотстоящих кадров и укладываются сеткой 4×3 одинаковых клеток (`<id>_idle.png`, клетка — самый большой кадр; центр по ногам, пол — одна линия, как у стойки, поэтому героя не «дёргает» при смене текстуры; сетка, а не лента — чтобы текстура не выходила за 4096 px). В игре это `spritesheet` (`CharacterLoader.queueCharacter`, размер клетки — в `characters.json`).

**Очередь, а не все сразу** (`systems/LiveStand.ts`, `IDLE_ANIM` в `Constants.ts`): «дышит» один из семи (шесть героев и лидер) — `TURN_MS` = 40 с, затем эстафета следующему, по кругу, ≈5 минут на круг; кто занят (удар, падение, сон, смена героя), тот пропускается. Так картинка никогда не застывает полностью, а анимируется всего одна фигура. История: сначала дышали все сразу, но при 10 кадрах в секунду в простое это смотрелось дёргано («очень мало FPS»), а повышать частоту для всех — значит снова грузить слабые ноутбуки; поэтому одна фигура и частота «ambient» (20 кадров в секунду) на время её хода (`GameEvents.LIVE_STAND` → `PowerSaver.liveStand`). Кадры стойки меняет таймер раз в `FRAME_MS` (100 мс, это ≈10 кадров анимации в секунду на 20 отрисованных), а не бесконечный твин. Во время удара, падения, сна и смены героя стойка стоит на статичном кадре. PNG героев хранятся палитровыми (256 цветов, `save_png`): на пиксель-арте разницы не видно; 30 героев ≈ 12 МБ.

**Лидер филиала** (`LeadSprite`): тоже «дышит» в своей очереди; на каждую продажу выбегает кадрами бега на `IDLE_ANIM.LEAD_DASH_PX` (55 px) в сторону героев, разворачивается и возвращается (если предыдущая пробежка ещё идёт — только импульс масштаба и искры); при победе бежит на месте (кадры бега переключает тот же бесконечный твин пульсации, без отдельного таймера).

### Что пробовали и почему отказались
- **Пиксельные чиби** (Classic Hero-семейство DezrasDragons/Umz, CC0): не понравились — «чиби» и слишком мелкая пиксельность рядом с нарисованным драконом.
- **3D-модели Quaternius → 2D-рендеры** (Ultimate Animated Character Pack, 30 героев): «выглядят как пластиковые игрушки, не тот характер».
- **Милые монстры Quaternius** (21 маскот): отклонены («монстры не нравятся, нужны серьёзные герои»). Герои-приключенцы Quaternius (RPG Characters: воин, маг, разбойник…) выглядели лучше, но их всего шесть, и 3D всё равно «пластмасса».
- **Нарисованные ИИ в стиле московских** (локальный Fooocus): лучшее попадание по стилю, но нужен запущенный Fooocus и день-два работы; архитектура уже позволяет добавить таких героев позже (добавить в `characters.json` + спрайты) без изменений кода.

## Раскладка сцены (`Constants.ts`)

Принята пользователем 2026-10-11 после трёх вариантов: **дракон с горой золота** нарисован в `DRAGON.SCALE` = 0.9 от прежнего размера и сдвинут вправо (гора `MOUNT_X` 1010, дно `MOUNT_BOTTOM_Y` 530; всё остальное — те же значения, пересчитанные вокруг подножия горы: `BODY_X` 1030, `BODY_BOTTOM_Y` 424, `HIT_X/Y` 900/316), чтобы целиком помещаться в кадр, а герои не стояли у его морды. **Герои** — слоты `HERO.SLOTS` (x 195…635, шаг 88; задний ряд y 508, масштаб 0.70, передний y 578, масштаб 0.77) — заметно мельче дракона; рывок длиннее, поэтому `STRIKE_FRONT_X` = 875 (подножие горы) и `RUN_MS` 330. **Лидер** стоит слева на прежнем месте (`HERO.LEAD` x 100, y 540) и на ~12 % выше героев переднего ряда (масштаб 0.86): заметен, но не перетягивает внимание. Свечение золота в фоне (`GLOW_AT` в `tools/build-scene.py`) сдвинуто под гору вместе с ней. Если снова двигаете дракона — меняйте `DRAGON.*` вместе, `Dragon.ts` и `IdleMood` берут `DRAGON.SCALE` из констант.

## Таблички РГ (2026-10-12)

Просьба филиала: под/над каждым героем — табличка с группой и её руководителем, «ВШ1 • Измайлова И.» (короткий код группы, фамилия и инициал), в стиле присланного образца (тёмное дерево, тонкая золотая рамка, светлые буквы), но без герба; то же — в разбивке по группам слева сверху.

- **Где.** У заднего ряда (y 508) — над головой, у переднего (y 578) — под ногами: ряды идут лесенкой, и так табличка не закрывает соседа из другого ряда (так решил пользователь). Высота героя одна у всех (`HERO.TEXTURE_HEIGHT` 290 × `TEXTURE_SCALE` × масштаб слота), поэтому положение таблички считается, а не подбирается для каждого персонажа. Табличка стоит на месте слота, когда герой убегает бить, падает или спит — она подписывает место, а не фигуру. У лидера филиала таблички нет.
- **Как нарисована** (`objects/NamePlate.ts`): Graphics + Text, ширина по тексту; перерисовывается только при смене имени, никакой анимации (нагрузка на ноутбуки не меняется). Глубина 1000 — над героями, под эффектами ударов.
- **Рейтинг** (`Leaderboard`): строки того же вида, панель шире (270 px).
- **Кто РГ** меняется в админке без деплоя: вкладка «Герои», поле у каждой группы (вставленное полное ФИО превращается в «Фамилия И.»). Дальше как с героями: `setRoster {leaders}` → Script Properties `LEADERS` → публичный GET `leaders` → `RosterConfig.applyLeaders` (+ `localStorage`) → `LEADERS_CHANGED`. Значения по умолчанию — `ropMapping.json` `leaders`, только фамилия и инициал: репозиторий и сайт публичные.

## Импорт оплат из выгрузки (2026-10-12)

Админка, вкладка «Импорт»: выгрузка CRM «Детальные данные по оплаченным счетам» (.xlsx). Формат — как в проекте «stepper game» (`docs/IMPORT_FORMATS.md` там): строка заголовков ищется по названиям в первых 20 строках (бывает в 1-й, бывает в 3-й под шапкой), одна строка = позиция оплаченного счёта, последняя строка «Сумма заказа» — итог файла.

- **Разбор в браузере** (`src-admin/paymentsFile.ts`, SheetJS 0.20.3 с cdn.sheetjs.com — та же версия, что в stepper game; npm-версия 0.18.5 с известными уязвимостями не годится). Библиотека грузится отдельным чанком только при выборе файла. На бэкенд уходят только дата оплаты, сумма, код группы и номер счёта; клиенты, ИНН, продукты остаются в браузере.
- **Правила.** Группа узнаётся по «ВШ<число>» (`systems/Groups.ts`, то же сопоставление, что в игре; в таблицу пишется короткий код); чужие группы не загружаются, только перечисляются. Позиции одного счёта складываются в одну строку таблицы. «Академия» (30 ₽) считается — игра для направления Академий. Сумма всех строк сверяется с «Суммой заказа».
- **Повторный импорт = замена периода** (выбор пользователя): все оплаты таблицы с датами от первой до последней даты оплаты в файле — и импортированные, и внесённые вручную — заменяются строками файла; остальные дни не трогаются. Плюсы: пересекающиеся выгрузки (1–8, потом 1–10 октября) ничего не задваивают, отменённая в CRM оплата исчезает. Риск: выгрузка не по всем группам обнулит отсутствующие. Поэтому сначала **пробный прогон** (`dryRun`): по каждой группе «сейчас за период → станет», строка с уменьшением подсвечена, отдельное предупреждение для группы, которой нет в файле; если в файле нет ни одной ВШ-группы, кнопка загрузки неактивна.
- **Запись в лист** (`importSales` в `Code.gs`): один `setValues` по строкам продаж (оставшиеся + новые, по дате; лишние строки очищаются) — без удаления строк и без момента, когда старое стёрто, а новое ещё не записано. Меняются только Date/Amount/ROP/Invoice. Колонку `Invoice` (текстовый формат) добавляет первый импорт.

## Страница руководителей групп (2026-10-15)

Просьба: отдельная «админка РГ» с одной функцией — внести оплату; у каждого из шести РГ свой PIN, по нему понятно, чья группа.

- **Страница** `rg.html` (третья точка входа Vite, `src-rg/main.ts`; стили — общие с админкой). После входа: «ВШ1 • Измайлова И.», сумма группы за неделю, форма «сумма + дата». Группу выбрать нельзя — её знает сервер по PIN (`groupLogin`, `groupAddSale`), поэтому РГ не внесёт оплату за чужую группу. Дата — «сейчас» или день текущей недели не позже сегодняшнего (выбор пользователя: можно донести забытое, но не трогать прошлые недели и будущее); сервер проверяет то же.
- **PIN-коды** создаёт админка (выбор пользователя): вкладка «PIN-код» → «Создать PIN для всех групп» или «Новый PIN» у одной группы. Случайные 6 цифр (`crypto.getRandomValues`), показываются один раз с кнопкой «Скопировать» (строки «ВШ1 • Измайлова И. — 123456» и ссылка на страницу); на сервере — только солёный хеш (`GROUP_PINS`). Пользователь сначала просил «придумай PIN» — не стали: PIN, прошедший через чат, считается засвеченным (так было с московским админским), а вписывать пароли в настройки Google за пользователя Claude не может.
- **Разделение прав.** PIN группы не открывает ни одного действия админки, админский PIN не работает на странице РГ; PIN-коды групп разные и не совпадают с админским (проверяется при выдаче и при смене админского PIN). Блокировка после 5 неверных PIN — своя у страницы РГ, админку не задевает. Новый PIN сразу отменяет старый (РГ со старым PIN при следующей оплате попадает на экран входа) и снимает блокировку.
- **С импортом**: ручные оплаты РГ — быстрый сигнал «здесь и сейчас»; когда админ загрузит выгрузку CRM за те же дни, она заменит их, двойного учёта нет.

## Удары по очереди (2026-10-12)

После импорта один опрос приносит деньги сразу нескольким группам. Раньше удары шли через 0,3 с — все герои бежали почти одновременно; пользователь попросил, чтобы каждый бил со своей задержкой. Теперь `diffAndEmit` складывает прирост по слоту (один удар на героя, даже если группа пришла под двумя написаниями) и выпускает удары **слева направо через `HERO.HIT_STAGGER_MS` = 1,2 с**: следующий стартует, когда удар предыдущего уже пришёлся и тот бежит назад. Шесть групп ≈ 7 с ударов, головы дракона падают после последнего. Действует для любого опроса, не только после импорта (обычно в опросе одна группа — разницы не видно).

## Фон

`tools/build-scene.py` собирает `bg_scene.jpg` (1280×720) из трёх слоёв пакета (небо, дальние горы, каменная арка; ×3 без сглаживания) и **сгенерированного песчаного пола** в палитре пакета с кристаллами/травой по краям. Пол начинается с y≈438: герои стоят на y 508/578, подножие горы золота — y 530 (см. `HERO.SLOTS`, `DRAGON.MOUNT_*`). Пак — яркий розовый закат, а нужна мрачная пещера дракона, поэтому `grade()` в скрипте затемняет (×0.6), обесцвечивает (×0.72), охлаждает тени, добавляет виньетку, темнит пол к краю кадра и подсвечивает тёплым свечением кучу золота (оно остаётся самым ярким в кадре). Параметры — константы `DARKEN`, `DESATURATE`, `TINT`, `VIGNETTE`, `GLOW_*` вверху блока. Если меняете фон — сохраните геометрию пола или поправьте константы.

## Бэкенд

Тот же `Code.gs` + отличия: (1) таблицу создаёт сам скрипт — `setupSpreadsheet()` один раз из редактора, id хранится в Script Properties (`SPREADSHEET_ID`), в коде его нет; (2) действие `setRoster` (герои и РГ) и поля `roster`, `leaders` в GET; (3) допустимые цели команды `fall` — `slot_1…slot_6`; (4) действие `importSales` и колонка `Invoice`. Остальное (PIN хешем + блокировка после 5 ошибок, `addSale` пишет только Date/Amount/ROP в первую свободную строку, команды анимаций в Script Properties, `requestId`-дедупликация) — как в Москве. Подробности API — `apps-script/README.md`.

## Что не проверено вживую / открыто

- Реальные ноутбуки филиала: нагрузка с новыми текстурами (≈40 КБ на кадр, 28 в памяти) не измерялась; при высокой — `?scale=1`, `?fps=20`, см. CLAUDE.md.
- Перекрашенные варианты смотрелись на контактных листах, но не каждый по очереди на сцене; у части перекрасок (красный/ледяной/золотой Clinok) цвета получились бледнее оригинала.
- У героев один кадр стойки и один кадр удара (не считая цикла бега): индивидуальных поз победы/горя нет, при победе все «подпрыгивают» кодом.
- Импорт проверен на синтетической выгрузке того же формата (группы ВШ, вымышленные клиенты) через локальный мок и на настоящей выгрузке московского направления (разбор и сверка с «Суммой заказа»; групп ВШ в ней нет). Настоящую ульяновскую выгрузку и запись в живую таблицу (выпадающий список в `ROP`, текстовая колонка `Invoice`) первым проверит пользователь.
